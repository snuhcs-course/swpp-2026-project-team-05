# FrameLESS 전문 비교 분석: 정확도 우선 설계

2026-10-19 작업 기준 설계와 구현 현황. 새 Reader 경로를 실기사로 종단 확인한 뒤 기록했다. 아래에는 구현한 범위와 아직 검증할 점을 함께 적는다.

## 이번 작업의 구현 범위

- 제목·리드 중심 사건을 독립적으로 재검토해 부수 화제의 주장·검색어를 줄인다.
- 네이버 검색의 정확도순과 최신순, 사건 검색어 변형을 함께 모으고 검색 출처를 추적한다. Google 검색 기반 URL 발견은 실서비스 검증 전까지 선택 기능으로 둔다.
- 제목·요약만의 `unrelated` 판정이 본문 검증을 완전히 막지 않도록 하고, 비교 기사 본문의 사건 집중도와 전재 중복을 검토한다.
- 사실 관계 판단에 Gemini 3.8 Flash를 작업별로 사용하도록 구성한다. 팀 OpenRouter 키를 우선 사용하고 직접 Gemini 키는 대체 경로로 둔다. 실제 기사 정답 사례에서 품질은 아직 확인해야 한다.

이 브랜치의 API는 대표 검색 주장 최대 3개로 비교 기사를 찾은 뒤, Reader 전용 5단계에서 원본 전체 문장을 검토하고 중심 사건의 내용 단위를 별도로 만든다. 표시 비교 기사마다 전문을 대조해 대응 구간과 A–G 표현 차이를 반환한다. I1 ★는 독립 비교 기사 2건 이상에서 관찰 0건이고 별도 부재 재검토도 통과한 경우에만 표시한다. `reader_analysis`가 실패한 요청은 이미 확인된 비교 기사와 원문을 유지하되 `coverage=verified_displayed_claims_only`/`i1_status=not_computed`로 되돌아간다.

## 판단: 검색은 두 경로, 판정은 수집한 본문으로

네이버 뉴스 API는 명시적인 기사 URL, 원문 URL, 게시일과 검색 출처를 준다. 모델의 웹 검색은 네이버 색인이 놓친 기사와 다른 어휘의 기사를 찾는 보조 경로로 사용한다. 두 경로의 URL을 합친 다음 본문을 서버가 직접 수집하고 확인한다. 검색 스니펫, 모델 요약, 인용 URL만으로 동일 사건이나 I1 부재를 판정하지 않는다.

검색 모델이 작성하는 사건별 검색어는 고유한 주체·행동·시점을 유지한다. 짧은 두 단어로 임의로 잘라 넓히지 않는다. 각 결과에는 검색 제공자, 검색어, 검색 시각, 검색 결과 URL과 최종 기사 URL을 보존한다. URL 정규화와 본문 유사도로 전재·중복 기사를 제거하되, 실제로 다른 매체가 독립적으로 보도한 기사를 섣불리 합치지 않는다.

## 단계와 품질 문턱

1. **원본 수집:** 공개 기사 URL을 검증하고 제목, 게시 시각, 추출 본문, 문장 ID와 정확한 본문 오프셋을 만든다. 본문이 너무 짧거나 제목·리드와 관계없는 추출 결과면 `extraction_uncertain`으로 표시한다.
2. **중심 사건 고정:** 제목·리드와 본문을 읽어 사건의 주체·행동·시점 및 근거를 추출한다. 본문 속 독립된 부수 사건은 원본에 실려 있어도 검색 범위와 I1 대상에서 제외한다. 불확실하면 중심 사건으로 단정하지 않는다.
3. **후보 발견:** 중심 사건의 여러 검색어로 네이버 뉴스와 선택적 웹 검색을 수행하고 후보 URL을 합친다. 메타데이터 순위는 본문 검증 순서를 정하는 힌트일 뿐, `unrelated` 판정만으로 본문 확인 기회를 영구히 없애지 않는다.
4. **본문 검증 및 선택:** 후보 본문을 확보한 뒤 동일 사건의 실질적 보도인지, 단순 언급인지, 다른 시점 사건인지 판정한다. 동일 사건의 반박 기사도 포함한다. 충분한 본문 근거가 있는 후보 중 원본 내용 단위의 대응 범위, 독립 매체, 표현의 다양성, 추출 품질을 기준으로 표시 기사 최대 3건을 고른다.
5. **원본 내용 단위:** 원본 전체에서 원자적 사실·주장 단위를 추출해 각각 한 원문 문장의 근거 구간에 연결한다. 여러 사실이 한 문장에 있으면 단위를 분리한다. 검색 단계의 대표 주장 최대 3개 제한을 여기에는 적용하지 않는다. 두 문장에 걸친 주장을 하나의 단위로 묶는 기능은 아직 없다.
6. **기사별 의미 정렬:** 각 비교 기사 본문에서 원본 내용 단위의 대응 문장을 찾고 관계를 `same`, `refutes`, `reframes`, `related_only`, `absent`, `uncertain`으로 기록한다. 인물·수치·단위·기준 시점·발언자 귀속이 다른 경우를 검토한다. I1 별표 후보의 부재는 별도 호출에서 제목과 본문을 다시 확인한다.
7. **표현 차이:** 원본과 비교 기사의 검증된 문장 쌍만 A–G로 분류한다. 정렬 단계에 더해 최대 18개 문장쌍을 한 번 더 검토하고, 초과하면 부분 검토로 알린다. 원본 표현이 평범해도 비교 기사와 차이가 있으면 원본 문장을 하이라이트한다. 여러 차이가 있으면 한 문장에 복수 카테고리를 연결한다. 직접 인용 안의 표현을 기자의 표현으로 돌리지 않는다.
8. **I1 집계:** 비교 기사에서 같은 내용을 반박해도 `observed`로 센다. 수집·정렬 실패와 `uncertain`은 `absent`로 바꾸지 않는다. 잠정 규칙은 성공적으로 검증된 동일 사건 비교 기사 2건 이상에서 관찰 0건인 중심 사건 내용에만 ★를 붙이는 것이다. 사용자 문구는 “이번 비교 기사 N건에서는 확인되지 않음”으로 한정한다.
9. **응답 검증:** 모든 인용문과 범위가 고정된 추출 본문의 실제 문자열과 일치하는지 서버에서 확인한다. 모델 판단, 검증된 증거, 보류 상태를 분리해 전달한다. 부분 실패는 하이라이트나 별표를 만들어 채우지 않는다.

## 모델 사용

후보 메타데이터의 거친 순위에는 Flash Lite, 사건 범위·본문 검증·의미 정렬·A–G에는 Gemini 3.8 Flash를 우선한다. 팀 예산의 OpenRouter 경로에서는 모델 ID `google/gemini-3.8-flash`를 쓴다. Pro 계열은 한국어 기사 정답 사례에서 개선이 확인될 때만 도입한다. 검색 결과가 아니라 서버가 수집한 본문을 모델 입력의 근거로 사용한다. 탭, 세로 드래그, 좌우 기사 넘김에는 모델 호출이 없다.

호출마다 작업명, 모델, 입력·출력 토큰, 비용 추정, 지연, 재시도, 검증 성공·보류 수를 기록한다. 운영 로그에는 API 키, 기사 본문, 프롬프트, 모델 원문 응답을 남기지 않는다. 동일 기사·동일 모델·동일 프롬프트 버전의 성공 결과는 재사용할 수 있게 한다.

기존 5단계 루브릭은 원본과 표시 기사 각각의 I1–I5 분석 1회와 대표 주장 각각의 A–G 분석 1회가 필요했다. 3개 표시 기사·5개 주장이면 기본 9회이며 검증 수리 호출은 별도였다. 새 Reader 경로는 I2–I5 출력을 생략하고, (1) 원본 전문에서 중심 사건 문장의 원자적 내용 단위와 위치를 만들고, (2) 표시 기사마다 모든 단위의 대응 구간·관계와 검증 가능한 A–G 차이를 만들며, (3) 검증된 문장쌍의 표현 차이를 한 번 더 검토한다. 일반 길이 기사의 기본 호출은 2+표시 기사 수이며, 긴 기사는 원본 36문장·내용 단위 18개씩 나눠 호출한다. 별표 후보에는 비교 기사 제목과 전문을 묶어 별도 부재 재검토 1회를 추가한다. 이 재검토가 실패하면 ★를 보류한다.

## Reader 응답 계약

- `source_article`, `related_articles`: 원본과 선택 기사들의 추출 전문, 제목, 원문 URL, 문장 ID 및 본문 오프셋.
- `highlights`: 원본 문장에서 A–G 표현 차이가 검증된 위치와 관련 비교 쌍.
- `pairs`: 원본·비교 기사의 대응 문장 위치, 관계와 구체적인 표현 차이. A–G가 없는 대응 문장도 기록된다.
- `i1_stars`, `i1_status`: 별표 문장의 검증 대상 독립 기사 수와 별표 보류 상태.
- `coverage`, `article_failures`, `analysis_status`: 실제 검토 범위와 부분 실패 상태.

Python 문자열 오프셋은 Unicode 코드포인트 기준이지만 Android 텍스트 범위는 UTF-16 기준이다. 응답에서 좌표 단위를 명시하고 변환 시 다시 원문 부분 문자열과 대조한다. 같은 구절이 반복될 수 있으므로 앱에서 `indexOf`로 위치를 다시 찾지 않는다.

## 실기사 확인 현황

2026-10-19 공개 기사 한 건을 **직접 Gemini 키**와 NAVER 연결로 실행했다. Gemini 3.8 단일 호출과 NAVER 검색은 연결됐고, Google 검색을 켠 첫 종단 시도에서는 검색·본문 검증 후 동일 사건 기사 6건을 찾았지만 루브릭 단계에 이르기 전에 직접 Gemini 경로에서 429가 반복됐다. Google 검색을 끄고 검색 후보 12건·표시 기사 최대 2건으로 다시 실행했을 때도 입력 주장 3개, 검색 후보 12건, 수집 본문 8건까지 진행한 뒤 후보 의미 검증 호출이 429로 제한됐다. 후자는 같은 사건·루브릭 결과를 만들지 못했다. 두 실행 모두 완성 데모 검증이 아니다. 직접 키의 429가 분당 요청량, 분당 토큰량, 일일 할당량 중 무엇 때문인지는 프로젝트 할당량 화면이나 구조화된 응답을 확인하기 전까지 단정하지 않는다.

같은 날 팀 **OpenRouter 키**로 엄격한 JSON 스키마 단일 호출을 확인했다. 첫 종단 실행은 검색 후보 12건 중 같은 사건 기사 1건을 찾았지만 여러 모델 응답 시간 초과와 형식 오류로 240초에 중단됐고, 이 호출의 키 사용액은 약 $0.19였다. 검색 후보 8건·주장당 최대 2건·표시 기사 최대 2건으로 줄인 Reader 종단 실행은 동일 공개 기사에서 124초, 제공자 보고 비용 약 $0.124로 완료됐다. 검색 후보 8건, 검증 후보 8건, 같은 사건 2건, 원본 내용 단위 8개, 비교 기사 전문 정렬 2건을 반환했고 오류 코드는 없었다. 이 사례에서는 I1 ★와 A–G 하이라이트가 0건이었다.

A–G 전용 재검토를 추가한 뒤 같은 기사를 다시 실행한 결과 137초, 제공자 보고 비용 약 $0.139로 완료됐다. 검색 후보 8건·검증 후보 8건·같은 사건 3건, 원본 내용 단위 6개, 표시 기사 전문 정렬 2건을 얻었고 A 카테고리 하이라이트 1건이 응답에 생성됐다. 별표는 0건이었다. 전용 재검토는 문장쌍 12개를 확인했으나 새로운 finding은 추가하지 않았고, A finding은 본문 정렬 단계에서 나왔다. 이 실행은 종단 성공을 입증하지만, 한 사례만으로 A–G 재현율이나 I1 의미 정확도를 확정하지 않는다.

## 평가 기준

실제 팀 기사에 사람이 확인한 정답을 만들어 검색 후보 재현율, 같은 사건 오검출, 부수 사건 유입, 문장 대응 누락, A–G 정확도, I1 ★ 오탐과 보류율을 단계별로 본다. 단순 JSON 형식 통과나 모델 호출 횟수를 의미 정확도 대신 사용하지 않는다. 어떤 변경도 위 품질 지표가 개선되지 않으면 운영 모델과 API에 반영하지 않는다.
